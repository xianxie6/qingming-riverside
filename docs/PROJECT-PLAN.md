## 1. 项目定位

**一句话**：把《清明上河图》“移步换景”的长卷观看方式，转成一个可以走进去、停下来、慢慢游历的网页街市。

**核心理念**（见 [项目缘起](PROJECT-STORY.md)）：

| 原则 | 含义 | 在产品中的体现 |
|---|---|---|
| 横向漫游 | 沿同一条汴河连续移动，不在页面间跳转 | 6516 世界单位长卷、连续行走、街区定位 |
| 日常叙事 | 重点是饮茶、送货、织作、撑篙等细小活动 | 141 位岸上人物、六组街区连续事件 |
| 水陆相接 | 河、码头、渡船、虹桥是结构，不是背景 | 招船乘船、虹桥过船、水磨落水 |
| 时间变化 | 同一条街在昼夜、雨中、四季中重看 | 北京时间昼夜与月相、时雨、四季底图与服装 |

**明确不做**：不使用原画扫描或裁切；不复刻具体建筑和人物；不做任务面板、积分、倒计时；不在画面上堆说明文字；不追求写实模拟或史料级复原。

**作品性质**：个人原创艺术项目，公开展示，未授予复用和商用许可（见 [LICENSE](../LICENSE)）。

## 2. 需求梳理

### 2.1 用户与场景

- **X 上的访客**：从帖子里的视频或动图点进链接，无需安装和登录，电脑或手机直接打开，停留几分钟。这是当前最主要的流量来源。
- **文化与设计爱好者**：愿意慢慢看细节、放大、切季节和夜景，会反复回访。
- **潜在合作方**：看作品质量与技术能力，关心授权和合作方式。

### 2.2 功能需求（按体验层级）

**L0 首页长卷**（`atlas.js`）
- 全幅长卷首屏；四个景点（水磨作坊、沿河茶市、虹桥烟火、城门货市）悬停淡彩，点击入画。
- 访问计数（Cloudflare D1）。

**L1 穿越**（当前唯一公开入口，`crossing*.js`）
- 滚动或拖动控制木梁合拢与穿桥镜头；“启程”自动行舟约 36 秒，可暂停、倒退。
- 雾中庭院里颗粒聚成朱衣画师（桌面 16 万、移动 6 万颗粒），“走入汴京”进入街市。
- 背景音乐和声音开关；减少动态效果或没有 WebGL 时直接进入街市。

**L2 可行走街市**（`scene.js` 及配套模块）
- 画师沿街道和桥面行走，逐脚落地；方向键、屏幕箭头、拖动、缩放、全屏、跟随。
- 招船乘船（约 48 秒横渡）、饮茶、居民点击回应、六组街区连续事件。
- 虹桥过船：接绳、牵引、降桅、过桥，生成可下载的“助船／观船”画稿（保存在本机）。
- 环境：昼夜与月相、清明时雨、四季底图与服装、夜间灯火、GPU 水面与水磨。

**L3 本地实验池**（不进入公开发布包）

| 模块 | 入口 | 完成度 | 文档 |
|---|---|---|---|
| 古城烟火 V3.1 | `explore.html` | 448 人、25 个寻找目标、收藏册，本地可玩 | [EXPLORE-V3.1](EXPLORE-V3.1.md)、[CITY-FUSION](CITY-FUSION.md)、[VISITORS](VISITORS.md) |
| 街景左右扩展 | `extension-preview.html` | 春日底图、234 位静态人物、有限动画、花铺与作坊 | [STREET-EXTENSION-PLAN](STREET-EXTENSION-PLAN.md)、[STREET-WORKSHOP](STREET-WORKSHOP.md) |
| 中秋灯市 | `data-midautumn-enabled` | 完整，暂时关闭 | [SEASONAL-SCENES](SEASONAL-SCENES.md) |
| 节日烟花 | 首页 | 完整，已停用自动播放 | [fireworks](fireworks.md) |

| ~~时空镜~~、~~纸上汴京~~ | — | 2026-10-19 删除 | — |

### 2.3 非功能需求

- **零门槛**：纯静态站点，无登录；访问计数失败不影响体验。
- **跨设备**：桌面、手机竖屏和横屏；触控、键盘、鼠标都能完成主流程。
- **性能**：街市连续行走约 55 FPS（880×919）；穿越按屏幕面积限制像素，持续低帧率时自动降分辨率；首屏只加载必要素材。
- **降级**：没有 WebGL 时回退 Canvas 水面；支持减少动态效果；加载失败可重试；后台标签页暂停绘制。
- **无障碍**：按钮有可访问名称，有焦点管理，Escape 退出并回到原入口。
- **视觉一致**：淡墨、暖纸色、灰绿与赭色；成人约 62–68、主角 66 世界单位。
- **版权清晰**：发布素材走白名单，素材来源与待确认的授权都有清单。

## 3. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 语言与模块 | 原生 JavaScript（无框架、无 TypeScript） | 多数为 `defer` 经典脚本加 IIFE；街市由 `dynamic-loader.js` 按顺序注入；三维和可选模块用 ES Module 动态 `import()` |
| 2D 渲染 | Canvas 2D | 底图、人物网格变形、遮挡层、雨雪、夜景合成 |
| 3D / GPU | Three.js r186（本地 `vendor/`） | 穿越场景、实例化颗粒、GPU 水面 `ShaderMaterial`、墨线后处理 |
| 首页 | SVG + CSS | 遮罩、`feTurbulence` 纸纹、热点按钮 |
| 音频 | Web Audio | 本地 mp3，加上合成的雨声和交互音效；首次交互才创建音频上下文 |
| 本地存储 | `localStorage` | 画稿、助船记忆、季节选择、收藏册进度 |
| 构建 | 自写 `build-static.mjs` + esbuild（只做压缩） | 素材白名单 `public-assets.json`、发布裁剪 `crossing-release.mjs`、路径检查 `check-public-assets.mjs` |
| 测试 | `node --test`，207 项 | 逻辑、几何、时序、发布范围、性能约束；浏览器验证用 Playwright 加截图 |
| 素材管线 | imagegen 生成 → 编辑 → WebP；Python／Node 布局脚本 | 提示词存 `docs/prompts/`，原稿存 `art-source/` |
| 部署 | GitHub Pages（Actions）、Vercel、Cloudflare Workers | 三处都发布 `dist/`；Worker 提供 `/api/visits`，D1 存计数 |
| CI | GitHub Actions | PR 和 `master`：`npm ci` → `npm test` → `npm run build` → `wrangler --dry-run` → Pages |

**评价**：渲染几乎全在 Canvas 和 WebGL 里，框架带来的收益很小；直接控制绘制顺序、缓存和生命周期才是性能的关键，所以“无框架、素材驱动”是对的选择。代价是没有类型检查、全局变量多、脚本顺序和 `?v=` 版本号要人工维护。

## 4. 架构设计

### 4.1 页面与体验流

```text
index.html 首页长卷 (atlas)
  ├─ 穿越 (crossing) ──完成──► 可行走街市 (scene)
  ├─ 景点「点击入画」 ───────► 可行走街市（定位到对应街区）
  └─ [本地] 古城烟火 explore.html / 中秋灯市 / 孙羊正店 sunyang.html / 扩展预览 extension-preview.html
```

### 4.2 世界坐标

- 街市统一使用世界坐标 x = −2172…4344（宽 6516）、高 724。西区：水磨、陶作、织坊、菜市；中区：茶市、虹桥、亭台；东区：货市、城门、仓场。接缝重叠 100 单位。
- 扩展计划把世界扩到 −5430…7602（宽 13032），原有坐标不变，向两侧追加。

### 4.3 街市渲染分层（从后往前）

1. 底图：只缓存视口附近，不建整卷超宽画布（`scene-backdrop.js`）
2. 河面与 GPU 水层（`water-three.js`，失败时回退到 `water.js`），船只（`river-boats.js`）
3. 店内人物，然后是桌面、楼栏等遮挡层
4. 街上路人、推车人、主角（`movement.js` 逐脚定位与网格变形）
5. 桥栏前景遮罩（`bridge-railing.js`），水磨与木桩前景
6. 天气、夜景灯火、季节粒子（`weather.js`、`night.js`、`seasons.js`）
7. DOM 控制层（10 Hz 更新）

### 4.4 主要模块

| 职责 | 模块 |
|---|---|
| 场景、镜头、输入、命中 | `scene.js`（约 1250 行，核心） |
| 行人与渡船状态 | `world.js` |
| 人口、服装、着色 | `population.js`、`inhabitants.js`、`wardrobe.js`、`people-masks.js`、`people-frames.js` |
| 动作与步态 | `movement.js`、`featured-characters.js`、`workshop-actors.js` |
| 街区事件 | `street-life.js`、`street-details.js`、`bridge-event.js`、`bridge-art.js` |
| 环境 | `seasons.js`、`night.js`、`weather.js`、`water*.js`、`mill-wheel.js`、`sound.js` |
| 分区加载 | `districts.js`、`dynamic-loader.js` |
| 穿越 | `crossing.js`（入口与生命周期）、`crossing-three.js`、`crossing-world.js`、`crossing-motion.js`、`crossing-quality.js` 等 12 个 |
| 古城烟火 | `explore*.js`、`city-fusion*.js`、`collection*.js`、`visitors-data.js` |
| 街景扩展 | `extension-*.js`（14 个） |

### 4.5 各模块共同遵守的生命周期约定

- **点击才加载**重模块；加载过程中关闭，不会再弹出。
- **退出必释放**：几何体、材质、纹理、渲染目标、动画帧、监听器、`ResizeObserver`。
- **互斥暂停**：一个全屏体验打开时，暂停被遮挡的街市、烟花和声音。
- **与帧率无关**：动画按经过时间推进，测试覆盖不同刷新率。

### 4.6 发布模型

- 仓库根目录是完整的本地“试验场”；`dist/` 是经过白名单和裁剪的公开包。
- `crossing-release.mjs` 在构建时从 `index.html` 删除实验入口、样式和脚本，只保留穿越和街市。
- `build:all` 构建全部实验模块，仅供本地检查。

## 6. 现状评估

### 6.1 优势

1. **主线完整**：首页 → 穿越 → 街市，是一条可以公开的完整旅程。
2. **细节可信**：逐脚落地、手部持物、遮挡顺序、交接时只画一件物品，这些是作品质感的来源。
3. **工程扎实**：白名单发布、构建期裁剪、全面测试、三平台部署、CI。
4. **试验能力强**：从想法到可运行原型很快，这正适合“在 X 上测反响”的策略。

### 6.2 问题与风险

| # | 问题 | 影响 | 状态 |
|---|---|---|---|
| 1 | 已提交的 `index.html` 引用了未提交的时空镜、纸上汴京文件 | 新克隆的仓库在本地运行时出现 404 | ✅ 本次随模块删除一并解决（改动尚未提交） |
| 2 | 仓库体积大：`.git` 约 902 MB 且全为松散对象；`art-source/` 有 651 个原稿入库（约 618 MB） | 克隆、CI、备份越来越慢 | 待处理 |
| 3 | 公开包里的三首音频（`crossing-background`、`day-ambience`、`night-music`）授权仍是“待确认” | 公开传播越广，风险越大 | 待处理，优先级高 |
| 4 | 没有在真手机上测试过 | X 的访客大多用手机，首次体验可能卡顿 | 待处理，优先级高 |
| 5 | `build:all` 失败：`extension-workshop.js`、`river-boats.js` 引用的 23 个素材不在白名单里 | 实验模块无法完整构建检查；默认发布构建不受影响 | 本次之前就存在，待处理 |
| 6 | 只有一个全站访问总数，看不出每次 X 帖子带来多少访问 | 无法判断哪个想法真的有效 | 待处理（见第 8 节） |
| 7 | 没有类型检查；核心代码单行很长；脚本顺序和 `?v=` 靠人工维护 | 长期维护成本上升 | 逐步改进 |
| 8 | 文档分散（30 多份），季节图同时保留 PNG 和 WebP 两份 | 查找困难，发布包偏大 | 逐步改进 |

## 7. 产品策略：双轨并行

```text
          ┌──────────── 短期：创意试验轨（X） ────────────┐
想法 ──► 快速原型 ──► 录屏发 X ──► 看数据 ──► 判定 ─┬─► 毕业：进入主线打磨
                                                    ├─► 迭代：改进后再测一次
                                                    └─► 归档：移出项目（例：时空镜、纸上汴京）
          └──────────── 长期：主线打磨轨（网站） ──────────┘
                     定期发布 · 节令更新 · 体验与性能打磨
```

### 7.1 短期：在 X 上测试新想法

**原则**：想法可以多，但每个想法的投入要小，判断要快，结论要留痕。

**单个想法的流程（建议 1–2 周一个）**

1. **立项（半天）**：写一句话假设，例如“观众会喜欢看画中人物在雪夜收摊”。在 `docs/ideas/` 建一页，写下假设和打算看的指标。
2. **原型（3–5 天）**：在独立分支或独立预览页里做，不碰主线代码。只做能录成 15–30 秒视频的那一段，不追求完整可玩。
3. **发布到 X**：
   - 视频或动图放在第一条，前 3 秒就要出现最好看的画面。
   - 配一句中文，可以再加一句英文；链接放在回复里或第二条。
   - 尽量固定在每周同一时段发，方便比较数据。
4. **观察 72 小时**，记录到这个想法的页面：

| 指标 | 说明 |
|---|---|
| 曝光、视频观看完成率 | 画面是否抓人 |
| 点赞 ÷ 曝光 | 整体喜爱程度 |
| 收藏 ÷ 曝光、转发 ÷ 曝光 | 收藏代表“想以后再看”，转发代表“想给别人看”，比点赞更有价值 |
| 回复内容 | 是否有人问“在哪玩”“能做 XX 吗” |
| 链接点击、网站访问 | 是否真的带来访问（需要第 8 节的来源统计） |

5. **判定**：以自己最近 5 条帖子的中位数为基线。
   - **毕业**：互动率或收藏率明显高于基线（例如 1.5 倍以上），并且有人主动问怎么玩 → 进入主线排期。
   - **迭代**：数据接近基线，但评论里有明确的方向 → 按反馈改一版，再测一次（最多两次）。
   - **归档**：数据低于基线，自己也不满意 → 移出项目，在想法页写下原因。

**现有实验池的建议排序**

| 顺序 | 想法 | 理由 |
|---|---|---|
| 1 | 街景扩展：田畴、仓场、柳岸的长镜头慢游 | 素材已有，最容易拍出“画卷不断展开”的视频 |
| 2 | 古城烟火：寻人与收藏 | 玩法独立、能引发互动（“你能找到画中的 XX 吗？”） |
| 3 | 节令场景：冬至落雪、春节灯火 | 借节日热度；中秋灯市和烟花已有框架，可以直接复用 |
| 4 | 新想法 | 每次只开一个，先过上面的流程 |

### 7.2 长期：定期更新，打磨主线

**更新节奏**

| 周期 | 内容 | 例子 |
|---|---|---|
| 每两周 | 一次小更新：体验修正、性能、细节 | 人物动作、遮挡修正、加载速度 |
| 每月 | 一次功能更新：一个毕业的想法正式上线 | 新街区、新事件、新玩法 |
| 节令 | 结合传统节日的限时内容 | 冬至（12-22）、春节（2027-02-06）、元宵（2027-02-20）、**清明（2027-04-05）** |

**清明节是这个项目的“主场”**：建议把 2027 年清明作为一次大版本的目标，例如街景扩展全卷上线，加上清明时雨的升级。

**每次发布前固定执行**

- [ ] `npm test` 和 `npm run build` 通过
- [ ] 桌面和手机两个视口截图，控制台无错误

## 9. 建议

### 产品

1. **试验要多，投入要小。** 一个想法的原型控制在一周以内；能用 15 秒视频说清楚的，才值得做成完整功能。
2. **让数据和评论来决定毕业，而不是完成度。** 时空镜和纸上汴京都做得很完整，但效果一般；以后先发视频测反响，再决定是否深做，可以省下大量时间。
3. **守住“慢”的气质。** 新功能应当让人停留更久，而不是更刺激。之前停用烟花自动播放、不做任务面板，都是对的取舍。
4. **主线上线标准**：文件全部提交、测试覆盖生命周期和降级、真机通过、性能达标、素材授权确认、有自然的入口和返回路径。

### 技术

1. **数据驱动**：街区、人物、事件、季节素材都抽成数据表，代码只负责读取和渲染。
2. **低成本类型检查**：给核心模块（`scene`、`world`、`movement`、`districts`）加 JSDoc，在 CI 里用 `tsc --checkJs --noEmit` 检查，不必迁移到 TypeScript。
3. **自动缓存版本**：构建时用内容哈希替换手写的 `?v=`，避免漏改导致访客看到旧版本。
4. **拆分 `scene.js`**：分成“镜头与输入”“绘制编排”“命中与交互”三部分。
5. **试验代码隔离**：每个想法一个分支或一个独立预览页；被归档时整体删除，不留残余引用（这次清理时就发现了好几处）。

### 流程

1. **小步提交**：每到一个能运行的小里程碑就提交，避免模块长期停留在未提交状态。
2. **结论留痕**：每个想法无论成败，都在 `docs/ideas/` 留一页“假设—数据—结论”。半年后回看，这就是你对受众最好的理解。
3. **每个阶段结束时更新本报告**，特别是第 6 节“现状评估”和第 8 节“路线图”。
